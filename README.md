# تمرین ۱ درس LLM Agents

## معرفی

این پروژه یک Agent استدلالی محلی است که سؤال را از فایل JSON
دریافت می‌کند و پاسخ نهایی را در فایل JSON دیگری می‌نویسد.

تمام فراخوانی‌های مدل از طریق Ollama نصب‌شده روی همان سیستم
انجام می‌شوند. برنامه به دیتاست، سرویس ابری یا اتصال اینترنت
در زمان ارزیابی نیاز ندارد.

## فایل‌های پروژه

- main.py: پیاده‌سازی کامل Agent و رابط خط فرمان.
- requirements.txt: مشخصات وابستگی‌های Python.
- README.md: راهنمای نصب، اجرا و معماری.

## پیش‌نیازها

- Python 3.10 یا جدیدتر.
- Ollama نصب‌شده و سرویس محلی فعال.
- مدل دقیق اعلام‌شده توسط مدرس، نصب‌شده پیش از ارزیابی.

این برنامه فقط از کتابخانه استاندارد Python استفاده می‌کند.

## آماده‌سازی

بررسی نصب:

```text
python --version
ollama --version
ollama list
```

نصب وابستگی‌های Python:

```text
python -m pip install -r requirements.txt
```

فایل requirements.txt پکیج خارجی ندارد؛ بنابراین ممکن است دستور
فوق چیزی نصب نکند.

مدل مدرس باید پیش از قطع اینترنت دریافت شود:

```text
ollama pull EXACT_MODEL_NAME
```

عبارت EXACT_MODEL_NAME یک جای‌نگهدار است و باید با نام دقیق
مدل اعلام‌شده توسط مدرس جایگزین شود.

اگر سرویس Ollama فعال نیست، آن را اجرا کنید:

```text
ollama serve
```

اگر سرویس از قبل فعال است، نیازی به اجرای نمونه دوم نیست.

## انتخاب مدل

ترتیب انتخاب مدل:

1. آرگومان --model، در صورت ارائه.
2. متغیر محیطی OLLAMA_MODEL.
3. اگر هیچ‌کدام تنظیم نشده باشد و دقیقاً یک مدل نصب شده باشد،
   همان مدل انتخاب می‌شود.

اگر چند مدل نصب شده باشد و نام مدل تنظیم نشده باشد، برنامه
به‌جای انتخاب تصادفی، خطای واضح می‌دهد.

تنظیم مدل در Windows CMD:

```bat
set "OLLAMA_MODEL=EXACT_MODEL_NAME"
```

تنظیم مدل در PowerShell:

```powershell
$env:OLLAMA_MODEL = "EXACT_MODEL_NAME"
```

تنظیم مدل در Linux/macOS:

```bash
export OLLAMA_MODEL="EXACT_MODEL_NAME"
```

برای ارزیابی باید از مدل مدرس استفاده شود، نه یک مدل جایگزین.

## رابط استاندارد

```text
python main.py --input input.json --output output.json
```

نمونه ورودی:

```json
{
  "id": "demo_001",
  "problem": "What is 14 * 6? Return only the integer."
}
```

نمونه خروجی مورد انتظار:

```json
{
  "id": "demo_001",
  "answer": "84"
}
```

این مثال صرفاً رابط برنامه را نشان می‌دهد و پاسخ آن در کد
ذخیره نشده است.

فیلد id بدون تغییر منتقل می‌شود.
فیلد answer همیشه رشته است تا پاسخ‌های متنی و صفرهای ابتدایی
کدها حفظ شوند.

## معماری Agent

### مرحله اول: Solver مستقل

مدل مسئله را به روابط، محاسبات یا قیود مرتبط تبدیل می‌کند
و یک پاسخ پیشنهادی همراه با خلاصه کوتاه بررسی تولید می‌کند.

### مرحله دوم: Solver مستقل با رویکرد جایگزین

بدون مشاهده پاسخ مرحله اول، مسئله دوباره با دستور بررسی
جایگزین و دمای متفاوت حل می‌شود.

هدف، کاهش وابستگی به یک مسیر حل است؛ البته دو فراخوانی
یک مدل از نظر آماری کاملاً مستقل نیستند.

### مرحله سوم: Verifier

مدل، مسئله اصلی و پیشنهادهای معتبر را دریافت می‌کند.
از آن خواسته می‌شود قیود، محاسبات، کمیت خواسته‌شده،
شرایط مرزی و قالب خروجی را دوباره بررسی کند.

این مرحله صرفاً رأی‌گیری نیست و می‌تواند هر دو پیشنهاد را رد کند.
حتی هنگام توافق دو Solver نیز بررسی نهایی اجرا می‌شود.

### بازیابی پاسخ نامعتبر

اگر پاسخ نهایی از نظر ساختار قابل استفاده نباشد، در صورت
باقی‌ماندن بودجه، حداکثر یک فراخوانی بازیابی انجام می‌شود.

### مسیر جایگزین

اگر بررسی نهایی و بازیابی شکست بخورند، از پاسخ‌های معتبر
Solverهای مستقل استفاده می‌شود.

انتخاب بر اساس تعداد تکرار دقیق پاسخ است؛ در تساوی، پاسخ
اول انتخاب می‌شود. توافق نامزدها تضمین‌کننده صحت نیست.

## تعداد فراخوانی و تنظیمات

در حالت معمول سه فراخوانی inference انجام می‌شود.
با بازیابی، حداکثر چهار فراخوانی انجام می‌شود.

درخواست‌های دریافت مشخصات مدل، inference محسوب نمی‌شوند.

تنظیمات پیش‌فرض:

- حداکثر فراخوانی: 4
- بودجه زمانی هدف کل: 300 ثانیه
- مهلت هر درخواست: 90 ثانیه
- سقف تولید هر فراخوانی: 1800 توکن
- پنجره context درخواستی: 8192 توکن
- think: false

نمونه تغییر تنظیمات:

```text
python main.py --input input.json --output output.json --max-calls 3 --time-budget 180 --request-timeout 60 --num-predict 1400
```

این اعداد انتخاب مهندسی اولیه هستند و باید متناسب با سخت‌افزار،
مدل مدرس و محدودیت رسمی ارزیابی آزمایش و تنظیم شوند.

بودجه زمانی با بررسی زمان و timeout شبکه کنترل می‌شود.
این کنترل جایگزین محدودیت سخت زمان در سطح سیستم‌عامل نیست.
بسته‌شدن اتصال نیز تضمین نمی‌کند پردازش سمت Ollama فوراً متوقف شود.

اگر نسخه Ollama یا مدل، پارامتر think=false را نپذیرفت:

```text
python main.py --input input.json --output output.json --think auto
```

فعال‌کردن thinking می‌تواند هزینه زمانی و مصرف توکن را تغییر دهد.

## اجرای آفلاین

برنامه:

- فقط به آدرس 127.0.0.1 وصل می‌شود.
- از API ابری استفاده نمی‌کند.
- هیچ دیتاست یا مدلی دانلود نمی‌کند.
- هیچ دستور pull را خودکار اجرا نمی‌کند.
- مدل‌هایی با نام cloud یا مشخصات remote گزارش‌شده توسط Ollama
  را رد می‌کند.

برای اطمینان از رعایت کامل شرط تمرین، مدل باید واقعاً محلی باشد
و اجرای نهایی با اینترنت قطع‌شده آزمایش شود.

## مدیریت خطا و خروجی

- پاسخ مدل ابتدا به‌عنوان JSON بررسی می‌شود.
- answer باید رشته غیرخالی باشد.
- قالب‌های آشکاراً نامناسب، مانند Markdown کد یا پیشوند Answer:
  پذیرفته نمی‌شوند.
- قالب دقیق معنایی هر مسئله توسط دستور Solver و Verifier بررسی می‌شود؛
  این بررسی تضمین قطعی تطابق با ارزیاب نیست.
- لاگ‌ها فقط در stderr نوشته می‌شوند.
- فایل خروجی با جایگزینی اتمیک نوشته می‌شود تا احتمال باقی‌ماندن
  JSON نیمه‌نوشته کاهش یابد.

اگر هیچ پاسخ معتبری تولید نشود، برنامه در صورت امکان خروجی زیر
را با id ورودی می‌نویسد:

```json
{
  "id": "the_input_id",
  "answer": ""
}
```

در این حالت کد خروج برنامه 1 است و دلیل خطا در stderr ثبت می‌شود.
رشته خالی پاسخ درست محسوب نمی‌شود؛ فقط قالب فایل را حفظ می‌کند.

در صورت ورودی فاقد id، مقدار id خروجی خطا null خواهد بود.
خطای دسترسی نوشتن یا توقف اجباری فرایند ممکن است مانع تولید فایل شود.

## امنیت و محدودیت‌ها

این نسخه کد تولیدشده توسط مدل را اجرا نمی‌کند.
همه حل‌ها و بررسی‌ها از طریق مدل محلی انجام می‌شوند.

مزیت این انتخاب، نبود وابستگی به sandbox اجرای کد است.
محدودیت آن این است که محاسبات و بررسی قیود همچنان ممکن است
دچار خطای مدل شوند.

هیچ پاسخ آماده، تشخیص مستقیم سؤال Public، یا پاسخ مرجع در کد
وجود ندارد.

## روند توسعه و تفاوت با نمونه اولیه

در نمونه اولیه پروژه، مسائل GSM8K با llama-cpp-python بررسی شدند.
ایده‌های اصلی آن نمونه شامل تولید چند پاسخ، اصلاح و تجمیع پاسخ‌ها بود.

نسخه تحویلی بازطراحی شده است تا:

- به‌جای خواندن GSM8K، ورودی JSON مدرس را دریافت کند.
- به‌جای llama-cpp-python، از Ollama محلی استفاده کند.
- علاوه بر عدد، پاسخ متنی و کد را حفظ کند.
- تعداد فراخوانی‌ها را محدود نگه دارد.
- خروجی استاندارد قابل ارزیابی تولید کند.

اجرای کد Python و اصلاح خطای اجرای کد در این نسخه وجود ندارد.
بازیابی در این نسخه مربوط به پاسخ نامعتبر مدل است.

نتایج نمونه اولیه، نتیجه ارزیابی این نسخه محسوب نمی‌شوند.
برای این نسخه هنوز دقت اندازه‌گیری‌شده‌ای در این مستند ادعا نشده است.

## چک‌لیست پیش از تحویل

- مدل دقیق مدرس انتخاب شده باشد.
- اجرای رابط استاندارد موفق باشد.
- برنامه با اینترنت قطع‌شده آزمایش شود.
- id ورودی و خروجی یکسان باشند.
- answer فقط پاسخ نهایی باشد.
- بودجه فراخوانی و زمان با محدودیت مدرس هماهنگ باشد.
- کیفیت روی مسائل توسعه دیده‌نشده نیز بررسی شود.
